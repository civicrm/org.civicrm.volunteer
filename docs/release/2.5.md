# CiviVolunteer 2.5

CiviVolunteer 2.5 is a compatibility and hardening release for CiviCRM 6.16 that
also redesigns the project-management and public signup workflows. It preserves
the existing data model, URLs, permission names and APIv3 interfaces.

## Requirements

| | |
|---|---|
| CiviCRM | 6.16 or newer |
| PHP | 8.1 – 8.4 |
| Smarty | 5 |
| Other extensions | none |


## Redesigned workflows

Editing a project is now one five-step workflow — **Details**, **Shifts & roles**,
**Assign volunteers**, **Roster**, **Hours** — with a shared header (status,
capacity, public preview), unsaved-change warnings on the manual-save screens,
and per-row autosave on Shifts & roles. The same screens render as dialogs from
the management list and inside an event's Volunteers tab, so there are no longer
two different editing experiences.

**Volunteers > Manage Volunteer Projects** offers a List view (search, campaign
and beneficiary filters, active/archived/all, bulk actions, per-project staffing
and "Needs volunteers" badges) and a Dashboard view (metric cards, an attention
queue of shifts to staff and hours to log, "Up Next" and "This Week").

The public opportunity page and signup form were rebuilt: quick filters
(weekends / evenings / no fixed time), date-grouped shift cards, a sticky
"Your shifts" selection rail, a two-step signup with a commitments sidebar and
an "I am bringing other people" disclosure for group registration. Selections
survive filter changes and a return trip from the details step.

Hours logging supports one shift or the whole project, every enabled activity
status, bulk mark-attended and set-hours operations, walk-in volunteers, notes
and commendations, saving as a single transaction. The Roster step groups
volunteers by date with search, status filters, selection-led email, per-row
Email/Call/SMS, printing and CSV export.

A new SearchKit-based **Volunteer Hours** report (**Volunteers > Volunteer Hours
Report**, and the *Hours report* project tab) provides headline totals, a
volunteer summary and assignment detail, backed by the read-only
`VolunteerHoursReport` API4 entity. The classic *Volunteer Report* template
remains and gains campaign and associated-event dimensions.

## CiviEvent and CiviCampaign

- The event Volunteers tab now boots the canonical project workflow instead of a
  second, competing interface, and its route, gate and permissions agree.
- Copying an event copies its volunteer project (shifts, roles, profiles — not
  assignments); deleting an event unlinks rather than deletes the project.
- The project → event link is declared as a dynamic foreign key, so API4 joins
  and SearchKit can traverse it; the associated event is shown on the management
  list.
- Campaign changes now propagate to historical (attended, no-show, cancelled)
  assignments and to commendations; campaign and event pickers, filters and
  report columns disappear gracefully when the components are disabled; a new
  project inherits its event's campaign.
- The public opportunity search offers a campaign filter, and event-linked
  signups redirect back to the correct event page.

## Security review

A comprehensive security review of the refactored extension (static audit,
public-surface and role-matrix dynamic review on a live site, client-side
and export audit, supply-chain review, remediation with regression
coverage) completed with **no open findings**. Behavioral changes shipped
from its remediation:

- The public signup page HTML-escapes beneficiary names before rendering
  the "Organized by" line (a crafted name could previously execute as
  markup).
- The signup form refuses projects that have no usable registration
  profile; such projects previously accepted submissions that created
  volunteer records with no contact behind them and consumed shift
  capacity.
- The shipped Volunteer Report instance now requires *edit all volunteer
  projects*, matching the roster and the hours report.
- A legacy pre-2.0 upgrade step validates its table identifier, and the
  PHPUnit run cache is excluded from release archives.

## Angular Profiles is no longer required

Earlier versions declared a hard dependency on **Angular Profiles**, which
existed only to load CiviCRM's legacy Backbone profile editor and expose it to
the project editor. That dependency is gone.

The project editor now uses a CiviVolunteer-owned profile picker: a select bound
to the profile ID, the audience selector, a read-only summary of the profile's
fields, and permission-aware *Create profile*, *Edit fields*, *Preview* and
*Refresh profiles* controls that open CiviCRM's own profile administration
screens in a new tab. Profiles created or renamed in that tab are picked up when
the project window regains focus.

Existing profile assignments are unaffected: they continue to live in
`civicrm_uf_join` with the same module, entity table, entity ID, weight and
`module_data` audience JSON. No migration is required.

**After upgrading**, confirm the project editor and public signup behave as
expected, then disable Angular Profiles. Keep it installed-but-disabled for one
rollback window before removing it, and check that no other extension declares a
dependency on it first.

## API changes

* The extension's runtime PHP and JavaScript are now API4-first: every internal
  APIv3 call has been converted. The API4 entities are `VolunteerProject`,
  `VolunteerNeed`, `VolunteerProjectContact`, `VolunteerAssignment`,
  `VolunteerCommendation`, the read-only `VolunteerHoursReport` view, and the
  `VolunteerUtil` helper. Checked reads are scoped to global managers or the
  projects the active contact owns/manages. Public project and need reads are
  limited to active public opportunities and public fields; project-contact
  rows are never exposed through public-registration access. Trusted
  `checkPermissions(FALSE)` reads remain explicitly unscoped.
* API4 create/update actions retain CiviCRM's standard formatting, custom-field,
  field-permission, output, and reload pipeline while routing persistence
  through the same guarded Volunteer BAOs as APIv3. Delete permissions preserve
  the APIv3 `delete own`/`delete all` contract.
* Purpose-specific API4 actions back the redesigned screens: aggregate project
  `commit`/`search`/`getManageOverview`/`getWorkflowContext`, public `VolunteerNeed.search` with
  `timeFilter` and `campaignId`, and on `VolunteerAssignment` the `getRoster`,
  `getHourEntries`, `logHours` and `getCapacity` actions (see
  [the developer API documentation](../dev/api.md)).
* All existing APIv3 entities, actions and result envelopes remain available as
  deprecated adapters over the API4 implementations, with one exception:
  `VolunteerUtil.loadbackbone` is removed along with the Backbone/Marionette
  management dialogs it existed to bootstrap. The Angular workflow replaced
  those dialogs earlier in this release, and nothing in the extension called
  the loader any more. The `civicrm/volunteer/backbonetemplates` route,
  `VolunteerUtil.loadBackbone` (API4) and `VolunteerProject.getManageData`
  (API4, superseded by `getManageOverview`) are removed with it.

### Breaking changes

Three changes can affect existing installations. Each is deliberate, and each
closes a case where the software was doing something other than what it
appeared to.

1. **The generic `setvalue` action is refused** on `VolunteerProject`,
   `VolunteerNeed` and `VolunteerProjectContact`. It wrote directly to the
   database without reaching any project authorization, so any caller who could
   satisfy the coarse permission map could edit rows belonging to projects they
   had no rights to. Use `create` with an `id` instead, which is guarded. Core
   has deprecated `setvalue` in favour of exactly that.

2. **The public opportunity page requires the *register to volunteer*
   permission.** `civicrm/vol` was previously reachable by anyone. Sites that
   already offer public signup grant this permission to the anonymous role
   already, because `civicrm/volunteer/signup` has always required it — but a
   site that used only the opportunity browser will need to grant it.

3. **Roster access follows project authority.** Viewing a project's roster now
   requires the ability to update that project (its owner, or a holder of *edit
   all volunteer projects*) or being one of its managers. Previously any holder
   of *edit own volunteer projects* could open any project's roster.

## Fixes worth calling out

* Public signup: capacity is verified under a row lock immediately before the
  assignment is written, and the whole registration — contact matching,
  assignment activities, custom values — commits or rolls back as one unit. A
  failure after commit while sending confirmation email is reported as a warning
  rather than discarding a saved registration.
* Opportunity search: the end of a date range now covers the whole final day.
  It previously stopped at 23:43:19 -- 16 minutes 40 seconds short -- because a
  fixed 85,399 seconds was added to midnight, which also gave the wrong boundary
  on daylight-saving transition days.
* Project locations are written to a private location block, so editing a
  project can no longer modify a location shared with an event or another
  project. Superseded location blocks are now cleaned up instead of accumulating
  on every edit.
* Deleting a project is refused while any volunteer assignment exists in any
  status, so completed volunteer history can no longer be orphaned.
* Deleting a dated need reparents every related assignment to the project's
  flexible need under a row lock while preserving status, dates, scheduled and
  completed time, and soft-deleted history.
* Soft-deleted assignments no longer consume opportunity capacity.
* Batch hour logging commits as a single transaction rather than leaving a
  partial batch behind when one row fails.
* The project profile picker now reacts immediately to selection and metadata
  refresh changes, and stable row identities prevent Select2 controls from
  inheriting another profile's value after a middle row is removed. Persisted
  profile, location, country, role, and beneficiary selections are also matched
  correctly when their AngularJS/Select2 controls initialize, and profile
  preview links use CiviCRM's required `gid` parameter.
* Project management now uses the nonpublic `civicrm/volunteer/manage` host so
  CiviCRM applies the configured backend theme. Historical bookmarks under the
  public `civicrm/vol` host redirect to the corresponding backend route. The
  public opportunity browser and signup form also render with the backend theme
  by default, so the whole volunteer workflow reads as one application; the
  **Use the backend theme on public volunteer pages** switch under
  **Volunteers > Configure Volunteer Settings** turns that off for sites whose
  public CiviCRM pages must follow the frontend theme.
* Every CiviVolunteer stylesheet reads its colours through one set of design
  tokens in `css/volunteer-tokens.css`, which maps Riverlea's theme variables
  (and the fallback for themes without them) once instead of in each file.
* Rich-text project and role descriptions are purified before display.
* Manager and beneficiary details reappear in confirmation emails, on the signup
  page and in the public search, where a permission-propagation bug had been
  silently dropping them.

## Schema

Upgrade revision 2500 adds a unique index on
`civicrm_volunteer_project_contact (project_id, contact_id, relationship_type_id)`,
an index for project entity lookups, an index for opportunity search, and
reconciles the expected foreign keys. It validates the data first and refuses to
run — naming the conflicting record IDs — rather than choosing which duplicate to
discard. Re-running it is safe.

No table is dropped or recreated by the upgrade. The extension's tables are now
defined once, in `schema/*.entityType.php`.

## Upgrading

1. Back up the database and the extension directory, and rehearse on a clone.
2. Deploy, then run `cv updb --no-interaction` followed by `cv flush`.
3. Verify project management, public signup, rosters, hour logging and the
   volunteer report.
4. Grant *register to volunteer* if the notes above apply to your site.
5. Disable Angular Profiles and re-check the project editor and public signup.

Rollback is a database restore plus the previous extension code. A code-only
rollback after revision 2500 is acceptable only if the older code tolerates the
additive indexes.
